# KA-001 — Cisco Console Access and Boot-State Identification

**Version:** 1.0  
**Status:** Draft — Validation Required  
**Knowledge Area:** Network Infrastructure  
**Applies To:** Cisco switches and routers used in SOTE lab environments  
**Related Missions:** OPS-001 Mission Backbone Forge

## Purpose

Use this Knowledge Article when a Mission Issue or Runbook requires you to connect to a Cisco network device by console and determine its current boot state.

This article is a reusable technical procedure. It does **not** authorize changes to a device. Your assigned Mission Issue defines what work you are authorized to perform.

## Expected Outcome

At the end of this procedure you should be able to:

- establish or attempt a local console session;
- recognize the general state the device is in;
- capture enough evidence for another technician or reviewer to understand what you observed;
- know when to stop and escalate instead of attempting recovery or configuration changes.

## Before You Begin

Confirm that:

- you have an assigned Mission Issue or other authorized work item;
- you have identified the correct physical device;
- you have an appropriate console cable or approved console connection method;
- you have an approved computer and terminal application available;
- you have a location to save relevant notes or console evidence.

If device identity is uncertain, stop and resolve the identity before connecting or changing anything.

## Stop and Escalate If

Stop and return to the assigned Mission Issue if:

- the device, power supply, cabling, or environment appears unsafe;
- you cannot positively identify the device you are about to work on;
- the device repeatedly reboots or behaves unpredictably;
- you encounter a password or credential boundary you are not authorized to bypass;
- the next step appears likely to erase configuration, files, or software;
- recovery would require an image, USB media, password recovery, ROMMON/boot-loader changes, or another procedure not authorized by the Mission Issue;
- you are uncertain what a prompt, message, or command will do.

Do not guess. Capture what you see and escalate.

## Procedure

### 1. Identify the Console Interface

Inspect the device and identify the available console interface. Depending on model, this may be a traditional RJ-45 console port, USB console port, or another manufacturer-supported local management interface.

Do not connect a cable to a network Ethernet port simply because the connector fits.

Record the device label/model and the console method used when that information is relevant to the assigned work.

### 2. Connect the Console Cable

Connect the approved console cable between the network device and the technician workstation.

If a USB adapter or USB console interface is used, allow the workstation to recognize the device before opening the terminal application.

### 3. Open a Terminal Session

Open the approved terminal application and select the serial/console interface associated with the cable.

For many Cisco devices using a traditional serial console, the common starting settings are:

```text
Speed: 9600 baud
Data bits: 8
Parity: none
Stop bits: 1
Flow control: none
```

These are common defaults, not permission to repeatedly change settings at random. If the assigned platform requires different settings, use the manufacturer documentation or an approved SOTE procedure.

### 4. Observe Before Changing Anything

With the console session open, press **Enter** once or twice if necessary to determine whether a prompt is already available.

If the device is powered off and the Mission Issue authorizes observing its startup, begin capturing the console session before power is applied so the boot sequence is preserved.

Do not immediately enter configuration commands, answer setup questions, reset the device, or interrupt the boot process.

### 5. Identify the General Boot State

Use the observed console output to place the device into one of these general categories.

#### Normal Operating-System Prompt

Examples may resemble:

```text
Switch>
Switch#
Router>
Router#
```

This generally indicates that the operating system has loaded. The prompt alone does not prove the configuration, software image, interfaces, or hardware are healthy.

#### Initial Setup Dialog

The device may display a question similar to whether you want to enter an initial configuration dialog.

Do not begin configuration simply because the dialog appears. Record the condition and follow the assigned Mission Issue or Runbook.

#### Boot Loader / Recovery Prompt

Depending on platform, you may see a low-level prompt such as:

```text
switch:
rommon>
```

This indicates that the normal operating system has not reached its standard operational prompt. **Do not begin recovery commands unless a Mission Issue or approved recovery procedure explicitly authorizes them.**

Capture the prompt and relevant messages, then return to the assigned work instructions.

#### Repeated Reboot / Boot Loop

The device repeatedly begins startup, generates errors, reloads, or returns to the beginning of the boot sequence.

Capture representative console output and stop. Repeatedly cycling power or experimenting with recovery commands can make diagnosis harder or create additional risk.

#### No Console Output

A blank terminal does not by itself prove the device is dead.

Check only the non-destructive basics within your authorized scope:

- correct serial/console interface selected;
- cable seated correctly;
- terminal session open;
- expected console settings selected;
- visible device power state.

If output remains absent, document the result. Do not start swapping hardware, resetting equipment, or changing unrelated settings unless authorized.

#### Other or Unknown State

If what you see does not clearly match one of the categories above, capture it as **UNKNOWN** rather than forcing a diagnosis.

Uncertainty is a reason to gather evidence and escalate, not a reason to experiment.

## Evidence to Capture

Capture enough information that another technician can understand the state without repeating unnecessary work. Depending on the mission, this may include:

- device label and model;
- console connection method;
- exact prompt observed;
- significant boot or error messages;
- whether the device remained stable or rebooted;
- photo or screenshot where appropriate;
- relevant console output saved as text where practical;
- your resulting classification: normal OS, setup dialog, boot loader/recovery, reboot loop, no output, or unknown.

Do not place passwords, secrets, private keys, or other credentials into GitHub comments or screenshots.

## Reporting Back to the Mission

Return to the assigned Mission Issue and use the work-log format required by that mission.

For OPS-001, a typical checkpoint is:

`CHECKPOINT — Console/boot state identified — Result/findings — Next step`

If you cannot safely continue:

`BLOCKED — What happened — What is needed to continue`

Put operational observations in the Mission Issue. Update this Knowledge Article only when you have learned something reusable that improves the procedure for future technicians.

## What This Article Does Not Cover

KA-001 does not authorize or teach:

- password recovery;
- deleting or resetting configuration;
- changing boot variables;
- formatting flash/storage;
- installing or replacing an IOS/software image;
- changing production network configuration;
- bypassing authentication or access controls.

Those activities require separate authorization and, where appropriate, their own Knowledge Article or Runbook.
