# KA-002 — Cisco Non-Destructive Discovery and Evidence Capture

**Version:** 1.0  
**Status:** Draft — Validation Required  
**Knowledge Area:** Network Infrastructure  
**Applies To:** Cisco switches and routers used in SOTE lab environments  
**Related Missions:** OPS-001 Mission Backbone Forge

## Purpose

Use this article when authorized work requires you to inspect a Cisco device without changing its configuration. The goal is to learn what is present, preserve useful evidence, and avoid turning discovery into configuration work.

This article does not authorize changes. The Mission Issue defines your scope.

## Expected Outcome

You should be able to identify basic device, software, configuration, interface, VLAN, neighbor, and health information and preserve findings for review.

## Before You Begin

Confirm that you have an authorized Mission Issue, the correct device, working console or approved management access, and a place to save evidence. If the device is not at a normal operating-system prompt, use KA-001 and follow the Mission Issue before proceeding.

## Stop and Escalate If

Stop if a command is unfamiliar, requires configuration mode, may alter state, exposes credentials/secrets, produces unexpected instability, or the device/platform does not match the procedure. Never enter configuration mode simply to continue discovery.

## Procedure

### 1. Confirm Identity

Start with non-destructive identification appropriate to the platform. Common Cisco examples include:

```text
show version
show inventory
```

Confirm the model and software context before choosing additional commands.

### 2. Capture Configuration State

When authorized and supported, inspect:

```text
show running-config
show startup-config
show boot
show flash:
```

Do not copy passwords, secrets, private keys, SNMP communities, or other sensitive values into GitHub comments or screenshots. Store sensitive configuration evidence only in an approved location.

### 3. Inspect Interfaces and Layer-2 State

Commands may include:

```text
show interfaces status
show vlan brief
show interfaces trunk
```

Record meaningful findings rather than pasting large amounts of unexplained output into the Mission Issue.

### 4. Inspect Neighbor Information

Where supported:

```text
show cdp neighbors detail
show lldp neighbors detail
```

Use neighbor information as evidence, not as proof that documentation or cabling is correct. Reconcile it with physical observations.

### 5. Inspect Health and Logs

Where supported:

```text
show environment all
show logging
```

If hardware alarms, repeated reloads, or serious errors appear, stop and report them according to the Mission Issue.

### 6. Summarize Findings

Capture the useful result: device identity, software version, boot/configuration state, key interface/VLAN/trunk observations, neighbor findings, hardware health, and unresolved questions.

## Evidence to Capture

Prefer concise evidence that another technician can verify: relevant command output, saved text, screenshots when useful, and a short interpretation. Do not store credentials or secrets in GitHub.

## Reporting Back to the Mission

For OPS-001, use the Mission Issue work log, for example:

`CHECKPOINT — Non-destructive discovery complete — Result/findings — Next step`

Use `BLOCKED — What happened — What is needed to continue` when safe progress is not possible.

## What This Article Does Not Cover

This article does not cover configuration changes, password recovery, software installation, resets, file deletion, VLAN creation, interface changes, or remediation. Those require separate authorization.

## Validation Checklist

Validate KA-002 on representative SOTE Cisco hardware and confirm that commands are appropriate to the actual platform, students can distinguish observation from modification, sensitive information is handled correctly, and the resulting evidence is useful to a reviewer.
